# Claude Code 設定の定期見直し

あなたは Claude Code のグローバル設定を見直して修正する担当です。カレントディレクトリは、設定を管理するリポジトリの作業用 worktree です。見直しの結果をもとにファイルを修正し、PR ディスクリプションを Markdown で出力してください（出力がそのまま PR の本文になる。push と PR 作成はこのあと自動で行い、merge は人が判断する）。

## 対象
- 修正するファイル（カレントディレクトリからの相対パス。既存ファイルの修正だけを行う）
  - `ansible/roles/claudecode/files/CLAUDE.md`（`~/.claude/CLAUDE.md` に配置される）
  - `ansible/roles/claudecode/files/claude-rules/`、`claude-agents/`、`claude-skills/`
- 読むだけのもの
  - 対象期間（末尾に記載）のセッション履歴: `~/.claude/projects/**/*.jsonl`（サブエージェントの履歴を含む。各行の `timestamp` で期間を判定する）
    - 履歴は大きいので、全体を Read しない。まず Grep で対象期間の行やキーワードに絞り込んでから、必要な箇所だけを Read する
  - 過去の見直し結果: `~/.claude/config-reviews/*.md`（同じ改善案を繰り返さない。人が merge しなかった改善案は再提案しない）
- `~/.claude/` 配下のファイルは編集しない（Ansible で上書きされるため）

## 調べること
1. ユーザーからの訂正・やり直し・強い口調の指摘。その原因になったルールの不足・曖昧さ
2. 繰り返し出てくる依頼・手順のうち、ルール・スキルにできそうなもの
3. サブエージェント・スキルの利用状況（呼ばれた回数、有効な指摘があったか）と、呼ばれていないもの
4. ルール同士の矛盾、守られていないルール、実態に合わなくなったルール

## 修正のルール
- 根拠（件数・具体例）がはっきりしている改善案だけを反映する。根拠が薄いものは反映も記載もしない
- 既存の文体・構成に合わせ、最小限の追記・修正にとどめる。ルールを増やすより、既存のルールを明確にすることを優先する
- 新しいファイルの追加、ファイルの削除、フック・スクリプト・Ansible タスクの変更が必要な改善案は反映せず、PR ディスクリプションの「反映していない改善案」に書く
- ファイルは public リポジトリで公開される。追記する文言・例文・PR ディスクリプションに、プロジェクト名・リポジトリ名・会社名・機能名・サービス名・環境構成・社内ドメイン・ホスト名・内部 API の仕様・個人名・メールアドレス・アカウント ID・個人の絶対パスを入れない。セッション履歴にあった具体例は、誰にでも当てはまる汎用的な表現に書き換える
- ユーザーの発言をそのまま引用しない。要旨を汎用的な表現で書く（PR ディスクリプションの根拠や、ルールの括弧内の例にも当てはまる）
- 業務の領域が推測できる語（扱っているデータや指標の名前など）を使わず、領域がわからない表現に言い換える（例: 「一部のデータだけで出した良い数値」）
- 出力する前に、差分と PR ディスクリプションを読み直し、上の 3 つ（固有名詞・発言の引用・業務の領域がわかる語）に当たる記述がないかを確かめる。このあと別の確認で 1 つでも見つかると、PR は作られない

## 出力（PR ディスクリプション）
以下の構成で、簡潔に書く。前置きやあいさつは書かない。

```markdown
## 概要
（3 行以内の要約。集計した範囲（期間・セッション数）を書く）

## 変更内容
（改善案ごとに「問題（根拠となる件数）」「変更（対象ファイルと内容）」「デメリット・リスク」）

## 反映していない改善案
（ファイルの追加・削除やフック・タスクの変更が必要なもの。なければ「なし」）

## QA手順
- 差分を読み、汎用的な表現になっているか、既存のルールと矛盾しないかを確認する
- merge 後に playbook の claudecode タグを実行して反映する
```

改善案がひとつもない場合は、ファイルを修正せず「改善案なし」とだけ出力する。
